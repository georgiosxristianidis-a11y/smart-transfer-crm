### P0-01 · PWA не существует. Offline = белый экран

**Severity**: CRITICAL  **Сложность**: M (~2ч)  **Делегат**: `lead`

**Файл**: [index.html](../../index.html) (нет регистрации) · [sw.js](../../sw.js) · [manifest.json](../../manifest.json)

**Симптом**: водитель в горах открывает приложение — не открывается ничего. Все данные на месте, но добраться до них нельзя.

**Корень**: в `index.html` **нет ни `navigator.serviceWorker.register()`, ни `<link rel="manifest">`**. Проверено по всей истории git — регистрация не появлялась никогда. То есть `sw.js`, `manifest.json`, `scripts/build-sw.mjs` и `kill-sw.html` — это ~150 строк кода, который никогда не исполнялся. `CLAUDE.md` при этом требует «после любой правки вызывать `npm run build:sw`» — ритуал вокруг мёртвого файла.

**Fix**:
1. `<link rel="manifest" href="manifest.json">` в `<head>`.
2. Регистрация SW после `load`, с обработкой ошибки (не молча).
3. Только после того как закрыты **P0-02** — иначе SW закэширует сломанное состояние, а cache-first его законсервирует.

**Гейт**: DevTools → Application → Service Workers = activated; Network → Offline → полная перезагрузка → приложение работает, график рисуется.

> **STOP**: только подключение SW/manifest и обработка ошибок регистрации. **Не** переписывать стратегию кэширования (это P1-08), **не** трогать `js/**`, **не** менять UI.

### P0-02 · Offline-калькулятор падает: рассинхрон Chart.js и `addAll`, который не переживает сеть

**Severity**: CRITICAL  **Сложность**: M (~2ч)  **Делегат**: `lead`

**Файл**: [index.html:15](../../index.html) · [sw.js:14](../../sw.js) · [scripts/build-sw.mjs:15](../../scripts/build-sw.mjs)

**Симптом**: даже после включения SW вкладка «Калькулятор» offline будет пустой.

**Корень** — три независимых дефекта в одной цепочке:

1. **Версии не совпадают.** Страница грузит `chart.js@4.4.0`, SW кэширует `chart.js@**4.4.1**`. Кэшируется URL, который никогда не запрашивается. Offline → `Chart` не определён → `new Chart(...)` в [calculator.view.js:222](../../js/calculator.view.js) бросает → рендер калькулятора мёртв.
2. **`ASSETS` в `sw.js` отстал от билд-скрипта**: нет `fuel.store.js`, `fuel.view.js`, `shared/flight.service.js`. Вкладка «Топливо» и весь Flight-модуль offline не загрузятся. `build-sw.mjs` тоже их не содержит — то есть `npm run build:sw` эту дыру не закроет.
3. **`cache.addAll` — всё-или-ничего.** В списке два кросс-доменных URL (jsDelivr, Google Fonts). Одна неудачная загрузка при установке → `addAll` реджектится целиком → SW **не устанавливается вообще**. Ставить SW при плохой сети — а именно так и будет у водителя — значит не поставить его никогда.

**Fix**: самохостить Chart.js и шрифты в репозиторий (это заодно снимает P1-07 про SRI и отсутствие CDN-контроля); сделать `ASSETS` единственным источником правды и генерировать его обходом файловой системы, а не ручным списком; критичные ассеты — `addAll`, необязательные — `Promise.allSettled`.

**Гейт**: `npm run build:sw` → в `sw.js` присутствуют все 8 JS-файлов; offline-перезагрузка → график рисуется; DevTools throttle «Slow 3G» при первой установке → SW всё равно активируется.

> **STOP**: `index.html` (теги подключения), `sw.js`, `scripts/build-sw.mjs`, добавление файлов вендоров. **Не** трогать бизнес-логику в `js/*.store.js`, **не** менять конфиг Chart.js и палитру графика.

### P0-03 · Единственная копия данных, ноль бэкапа, ошибки проглочены

**Severity**: CRITICAL  **Сложность**: L (~день)  **Делегат**: `lead`

**Файл**: [js/shared/db.js:20](../../js/shared/db.js) · [js/trips.store.js:11](../../js/trips.store.js) · [js/trips.view.js:121](../../js/trips.view.js)

**Симптом**: все трансферы исчезают. Пользователь не получает никакого сигнала — он видит «Поездок пока нет. Добавьте первую!», то есть **потеря данных визуально неотличима от чистой установки**.

**Корень** — четыре сходящихся дефекта:

1. **IndexedDB — единственное хранилище.** Нет экспорта по расписанию, нет второй копии. Очистка данных сайта, переустановка браузера или ITP-eviction на iOS (Safari удаляет хранилище сайтов, к которым не заходили 7 дней — а вне сезона так и будет) → всё стёрто безвозвратно. Экспорт CSV существует, но он ручной и его надо не забыть нажать.
2. **Ошибка загрузки проглатывается.** `loadInitialData()` ловит исключение в `catch`, пишет в `console.error` и оставляет `this.trips = []`. Консоль на телефоне никто не видит.
3. **Ошибка сохранения роняет форму.** `_getStore()` бросает `'IndexedDB not supported'`, если инициализация не удалась. `addTrip` вызывает `await this.db.saveTrip(trip)`; обработчик `submit` — `async` **без `try/catch`**. Результат: unhandled rejection, `form.reset()` и закрытие модалки не выполняются, поездка живёт только в памяти и умирает с вкладкой. Пользователь думает, что сохранил.
4. **Промис инициализации реджектится в пустоту.** `this.initPromise = this._init()` в конструкторе; `request.onerror` реджектит его, но на момент конструирования подписчиков нет → unhandled promise rejection при старте.

**Fix**: автоэкспорт снапшота в `localStorage` при каждой мутации (второй носитель с другим профилем вытеснения) + видимая пользователю плашка ошибки вместо `console.error` + `try/catch` в submit-обработчике с сохранением введённых данных + `.catch()` на `initPromise` в конструкторе + напоминание об экспорте раз в N дней.

**Гейт**: `npm test` (нужен новый тест на путь отказа DB) + ручной сценарий: DevTools → Application → Clear storage → перезагрузка → приложение **явно сообщает**, что данных нет и почему.

> **STOP**: `js/shared/db.js`, `js/trips.store.js`, обработчик submit в `js/trips.view.js`, плюс новый тест. **Не** вводить облачный синк и аккаунты — по решению владельца бэкенда нет. **Не** мигрировать `FuelStore` на IndexedDB в этой карточке (см. P3-05).

### P0-05 · Приложение выдумывает статус рейса и показывает его водителю как факт

**Severity**: CRITICAL  **Сложность**: M (~2ч)  **Делегат**: `lead`

**Файл**: [js/shared/flight.service.js:72](../../js/shared/flight.service.js) · [js/trips.view.js:398](../../js/trips.view.js)

**Симптом**: карточка показывает «🟠 Задержка +25м» и время прилёта. Водитель приезжает на 25 минут позже. Клиент ждёт в аэропорту. Рейса никто не проверял.

**Корень**: статус вычисляется так —

```js
const hash = flightCode.split('').reduce((acc, c) => acc + c.charCodeAt(0), 0);
if (hash % 5 === 0) { status = 'delayed'; delayMins = 25; ... }
```

Это **сумма кодов символов по модулю 5**. Никакого обращения к данным о рейсах нет и не было — в приложении вообще нет ни одного сетевого запроса. Ровно каждый пятый рейс «задерживается» ровно на 25 минут, детерминированно и вечно. Комментарий в коде честно называет это `Deterministic simulation for demo/testing`, но UI подаёт результат как живые данные: пульсирующая точка, цветной бейдж, надпись «В полете».

Усугубляет [trips.view.js:398](../../js/trips.view.js): кнопка **Sync** крутит спиннер 800 мс через `setTimeout` и выдаёт `alert('Рейс ... синхронизирован с радаром!')`. Никакой синхронизации не происходит — это анимация поверх пустоты, и она подтверждает пользователю достоверность выдуманного статуса.

**Fix** — выбор владельца, два честных варианта:
- **(a) Убрать обман**: оставить только распознанный код рейса и рабочую ссылку на Flightradar24 (она настоящая). Убрать бейдж статуса, ETA и кнопку Sync целиком.
- **(b) Сделать по-настоящему**: подключить API расписаний (AeroDataBox / FlightAware), добавить `connect-src` в CSP, кэш ответов, состояние «нет данных». Требует ключа и, вероятно, платного тарифа — при этом offline статус всё равно будет неизвестен.

Рекомендую **(a)**: за отсутствие данных никто не пострадает, за ложные данные — пострадает клиент и репутация.

**Гейт**: в `flight.service.js` нет ни одного `hash`/`Math.random`/`setTimeout`, формирующего пользовательский факт. Новый тест: `resolveFlightStatus` не возвращает `delayed` без внешнего источника.

> **STOP**: `js/shared/flight.service.js` и связанные блоки рендера бейджа в `js/trips.view.js`. **Не** удалять `extractFlightCode` и `getFlightRadarUrl` (они полезны и чинятся отдельно в P1-05), **не** трогать навигацию Google Maps / Waze.

### P0-06 · Экономическая модель завышает прибыль: нет налога на прибыль и нет стоимости самого минивэна

**Severity**: CRITICAL  **Сложность**: L (~день)  **Делегат**: `lead`

**Файл**: [js/calculator.store.js:87](../../js/calculator.store.js)

**Симптом**: «Честный день» показывает цифру, на которую нельзя опереться при решении входить в бизнес. Реальный результат заметно ниже.

**Корень** — что проверено и **корректно**: ставка НДС 13% для пассажирских перевозок в Греции применена верно (`checkGross / 1.13` — это именно вычленение НДС из брутто, а не вычитание 13%). Порт-сборы, износ по интервалам, ΕΦΚΑ на владельца, бухгалтер, страховка — на месте.

Чего **нет** в `totalExpenses`, при том что это крупные статьи:

1. **Налог на прибыль.** Полностью отсутствует. Для греческого ИП это прогрессивная шкала (9 / 22 / 28 / 36 / 44%) плюс `τέλος επιτηδεύματος`. На декларируемой прибыли это самая большая невключённая статья — по порядку величины сопоставима со всем топливом.
2. **Стоимость самого автомобиля.** Ни цены, ни амортизации, ни лизинга/кредита, ни остаточной стоимости. Минивэн в модели достался бесплатно и не изнашивается как актив — амортизируются только масло, сцепление и шины.
3. **Лицензия/номер такси (ΕΔΧ).** На Крите это существенный капитальный вход, в модели его нет.
4. **Простой.** `seasonDays` × `tripsPerDay` предполагает, что каждый день сезона отработан на полную. Нет ни болезни, ни поломки, ни дождя, ни коэффициента загрузки.
5. **ΤΕΛΗ ΚΥΚΛΟΦΟΡΙΑΣ**, ΚΤΕΟ, парковки, мобильная связь, комиссия платёжных систем.

**Спорные решения** (не ошибки, но требуют твоего явного ответа):

- **Резерв 5% учтён как расход** (`totalExpenses` включает `safetyNet`), то есть уменьшает «чистую прибыль». Но резерв — это отложенные твои же деньги, а не издержка. Сейчас цифра прибыли занижена на 5%, тогда как из-за пунктов 1–5 она завышена намного сильнее. Две ошибки в разные стороны маскируют друг друга — это худший вид неточности, потому что итог выглядит правдоподобно.
- **Чаевые не входят в прибыль**, показаны отдельно — корректно, но главный показатель «Честный день» их не включает, а водитель их получает. Нужно решить, что именно означает главная цифра.
- **Расход 8.7 л/100 км захардкожен** в [строке 101](../../js/calculator.store.js) и не входит в `state`. В калькуляторе, весь смысл которого — играть допущениями, ключевое допущение неизменяемо.

**Fix**: добавить в `state` налог на прибыль (ставка настраиваемая), капзатраты с амортизацией, коэффициент загрузки; вынести расход топлива в `state`; развести «Прибыль до налогов» / «После налогов» / «В карман каждому» как три разных числа; убрать резерв из расходов и показывать его как распределение прибыли.

**Гейт**: `npm test` — тесты на новую цепочку обязаны быть написаны **до** влития логики (требование `CLAUDE.md`). Сверка итога с реальной декларацией за прошлый сезон, если есть.

> **STOP**: `js/calculator.store.js` + `test/calculator.store.test.js` + подключение новых полей в `index.html`/`calculator.view.js`. **Не** менять дизайн-систему, не трогать график и палитру, **не** переделывать вкладки «Поездки» и «Топливо».

### P1-01 · Даты считаются в UTC — выручка съезжает на сутки

**Severity**: HIGH  **Сложность**: M (~2ч)  **Делегат**: `lead`

**Файл**: [js/app.js:23](../../js/app.js) · [js/fuel.store.js:79](../../js/fuel.store.js) · [js/trips.store.js:100](../../js/trips.store.js) · [js/trips.view.js:51](../../js/trips.view.js)

**Симптом**: ночные поездки попадают в неправильный день; выручка «Сегодня» и «Месяц» в шапке не сходится с фактом; в ночь на 1-е число месячная сумма считается неверно.

**Корень** — две разные ошибки с датами, обе системные:

1. `new Date().toISOString().split('T')[0]` даёт **UTC-дату**. Крит — UTC+3 летом. С 00:00 до 03:00 по местному времени эта строка возвращает **вчера**. Поездка, добавленная в 01:30 ночи, получает вчерашнюю дату по умолчанию, а фильтр «сегодня» её не находит. Встречается в четырёх местах.
2. `new Date(t.date)` для строки `'2026-08-14'` парсится по спецификации как **UTC-полночь**. Далее `d.getMonth()` возвращает месяц в **локальной** зоне. Для положительного смещения (Крит) совпадает, но для отрицательных смещений даёт предыдущий день — то есть поездка 1 августа учтётся в июле. Приложение молча зависит от того, что владелец не пересечёт нулевой меридиан.

**Fix**: одна утилита `todayLocal()` / `parseLocalDate()` в `js/shared/utils.js`, применённая во всех четырёх местах. Часовой пояс должен стать явной сущностью, а не побочным эффектом.

**Гейт**: новый тест с подменой часового пояса (`process.env.TZ`) на `Pacific/Kiritimati` (+14) и `Pacific/Midway` (−11) — суммы обязаны совпасть.

> **STOP**: `js/shared/utils.js` (добавить), четыре места вызова, новый тест. **Не** менять формат хранения дат в существующих записях — миграция здесь не нужна и опасна.

### P1-02 · «Следующий трансфер» показывает поездку из прошлого

**Severity**: HIGH  **Сложность**: S (<30м)  **Делегат**: `sonnet`

**Файл**: [js/trips.store.js:109](../../js/trips.store.js)

**Симптом**: главный герой-блок вкладки вечно показывает поездку недельной давности, которую забыли отметить завершённой. Настоящая ближайшая поездка не видна. HUD водителя открывает её же.

**Корень**: `getNextUpcomingTrip()` возвращает `activeTrips[0]` — просто первый элемент списка, отсортированного **по возрастанию даты**. Фильтра «в будущем» нет вообще. Любая незакрытая поездка из прошлого навсегда занимает первое место.

**Fix**: фильтровать по `datetime >= now` (с небольшим окном назад, скажем −2 ч, чтобы текущая поездка не исчезала на полпути) и отдельно показывать «просроченные, требуют закрытия».

### P1-03 · Детектор конфликтов пропускает половину реальных наложений

**Severity**: HIGH  **Сложность**: M (~2ч)  **Делегат**: `sonnet`

**Файл**: [js/trips.store.js:59](../../js/trips.store.js)

**Симптом**: две поездки в 45 минутах друг от друга не подсвечиваются, водитель берёт обе, опаздывает на вторую.

**Корень** — три дефекта в одной функции:

1. **Завершённые исключены из сравнения** (`filter(t => t.status !== 'completed')`). Но завершённая поездка занимала машину физически. Планируя новую на 10:15, когда на 10:00 уже стоит завершённая, конфликт не покажется.

**Fix**: включить завершённые в сравнение; вынести порог в настройки; явно помечать записи с невалидным временем как «требуют проверки», а не как «конфликта нет».

**Гейт**: `npm test` — кейсы «завершённая + новая через 20 мин → конфликт» и «пустое время → пометка, а не тишина».

> **STOP**: `getConflicts` + тесты + бейдж конфликта в рендере. **Не** внедрять расчёт длительности маршрута по географии (это отдельная большая задача).

### P1-07 · CSP декоративный, зависимости без контроля целостности

**Severity**: HIGH  **Сложность**: M (~2ч)  **Делегат**: `lead`

**Файл**: [index.html:6](../../index.html)

**Симптом**: заявленная в `CLAUDE.md` «жёсткая CSP» не защищает ни от чего.

**Корень**:

```
default-src 'self' 'unsafe-inline' 'unsafe-eval' https://cdn.jsdelivr.net ...
script-src-attr 'unsafe-inline';
```

- **Нет директивы `script-src`** → скрипты падают на `default-src`, где стоят `'unsafe-inline'` **и** `'unsafe-eval'`. Это отключает главную защиту CSP от XSS.
- `script-src-attr 'unsafe-inline'` **явно разрешает** инлайновые обработчики (`onclick=`) — ровно тот вектор, от которого CSP и существует.
- Нет `object-src 'none'`, нет `base-uri 'self'` (защита от подмены базового URL), нет `connect-src`, нет `form-action`.
- `frame-ancestors` в meta-теге не работает в принципе — нужен HTTP-заголовок.
- **Нет SRI** на `<script src="cdn.jsdelivr.net/...">`. Компрометация CDN = полный контроль над приложением, где лежат имена и адреса клиентов.

Прямо противоречит `CLAUDE.md`, который называет это «жёстким Content-Security-Policy».

**Fix**: самохостинг Chart.js и шрифтов (закрывает и P0-02 разом) → после этого CSP сжимается до `default-src 'self'; object-src 'none'; base-uri 'self'` и `'unsafe-eval'` уходит. `style-src 'unsafe-inline'` придётся оставить: код пишет инлайновые стили в `trips.view.js` (`style="opacity:0"`, `transform`) — либо оставить, либо переводить на CSS-классы отдельной задачей.

**Гейт**: DevTools Console при полном прогоне сценариев — ноль нарушений CSP; в политике отсутствует `unsafe-eval`.

> **STOP**: `<head>` в `index.html` + добавление вендорных файлов. **Не** переписывать инлайновые стили в `js/**` — это отдельная задача, иначе карточка расползётся.

### P1-08 · Кэш cache-first без обновления: пользователь застрянет на старой версии

**Гейт**: правка JS → `npm run build:sw` → перезагрузка → изменение видно без ручной чистки кэша. Второй кэш на origin переживает активацию.

### P2-01 · Экранирование HTML обходится массивом

**Severity**: MEDIUM (латентная)  **Сложность**: S (<30м)  **Делегат**: `lead`

**Файл**: [js/shared/utils.js:27](../../js/shared/utils.js)

**Симптом**: сейчас не эксплуатируется — но это заряженная мина под главной защитной функцией проекта.

**Корень**:

```js
if (Array.isArray(value)) return acc + string + value.join('');
```

Массив **вставляется в разметку без экранирования вообще**. Автор явно рассчитывал на массив уже готовых `SafeHTML`, но проверки типа нет. 1. **`touch-action` не задан нигде в CSS** (проверено — ноль вхождений). Браузер начинает нативную прокрутку одновременно с обработкой `pointermove`. JS-эвристика `Math.abs(diffY) > Math.abs(diffX)` срабатывает уже после того, как карточка визуально сдвинулась. Нужен `touch-action: pan-y` на `.swipe-content`.
2. **Нет обработчика `pointercancel`.** Когда браузер забирает жест себе (нативный скролл, входящий звонок, системный жест «назад»), `pointerup` не приходит. `draggingElement` остаётся заполненным, `transform` — применённым. Карточка залипает сдвинутой до следующего рендера.
3. Свайп вправо работает и на **уже завершённой** поездке, повторно вызывая `updateTripStatus(id, 'completed')` — лишняя запись в БД и лишняя вибрация.
4. Удаление подтверждается через `confirm()`, но **завершение — нет**. Асимметрия: ошибочное завершение (сдвиг вправо при прокрутке) происходит мгновенно и отменить его нельзя — операции «отменить завершение» в UI не существует.

**Fix**: `touch-action: pan-y`; обработчик `pointercancel` → `resetSwipe()`; игнорировать свайп вправо на завершённых; добавить «Отменить» с таймаутом вместо `confirm()`.

**Гейт**: на реальном телефоне — быстрая прокрутка длинного списка не сдвигает карточки и не оставляет залипших.

> **STOP**: `bindSwipeGestures` + правило `touch-action` в CSS. **Не** переделывать анимацию фоновых action-слоёв.

### P2-06 · Полная перерисовка списка на каждое изменение + конфликт View Transitions

**Severity**: MEDIUM  **Сложность**: M (~2ч)  **Делегат**: `sonnet`

**Файл**: [js/trips.view.js:409](../../js/trips.view.js) · [js/app.js:60](../../js/app.js)

**Корень**:

1. **`innerHTML` перестраивает весь список** при любом изменении — даже при смене статуса одной поездки. Теряется позиция прокрутки, заново парсятся десятки инлайновых SVG (в карточке их 3–5), пересоздаётся весь DOM. При 200+ поездок за сезон это заметная задержка на телефоне.
2. **`getConflicts()` — O(n²)** и вызывается внутри каждого `render()`, создавая по два объекта `Date` на сравнение. Для 300 поездок это ~45 000 итераций с двумя аллокациями каждая, на каждый чих. Само по себе при 1–3 водителях не критично, но складывается с пунктом 1.
3. **Вложенные `startViewTransition`.** `app.js` оборачивает переключение вкладок, `trips.view.js` — рендер списка. Спецификация допускает **только один активный переход**: второй вызов прерывает первый. Смена вкладки в момент обновления стора даёт визуальный сбой.
4. `getConflicts()` возвращает `Set`, который **пересоздаётся** на каждый рендер, хотя данные не менялись.

**Fix**: индексировать конфликты один раз по дате (`Map<date, trip[]>`) — O(n) вместо O(n²); кэшировать результат в сторе и инвалидировать при мутации; точечное обновление изменившейся карточки вместо полной перестройки; убрать вложенный View Transition.

**Гейт**: Performance-профиль с 300 поездками — перерисовка после смены статуса укладывается в один кадр.

> **STOP**: `render`/`getConflicts` и обёртки View Transitions. **Не** вводить виртуальный DOM и не тащить фреймворк — стек осознанно ванильный.

### P2-07 · Графическая нагрузка рассчитана не на телефон

**Severity**: MEDIUM  **Сложность**: M (~2ч)  **Делегат**: `gemini 3.7`

**Файл**: [css/style.css](../../css/style.css)

**Корень** (замерено по файлу):

- Три постоянных фоновых слоя (`.cosmic-bg`, `.horizon-beam`, `.particles-layer`) под всем приложением.

**Fix**: блок `@media (prefers-reduced-motion: reduce)`, отключающий все бесконечные анимации; сократить `backdrop-filter` до 2–3 ключевых поверхностей; в LHCI переключить пресет на `mobile`.

**Гейт**: LHCI в мобильном пресете + замер батареи/термалки на реальном устройстве за 30 минут работы.

> **STOP**: `css/style.css` и `.lighthouserc.json`. **Не** менять палитру и токены — «Air Minimalism» сохраняется, снимается только стоимость эффектов.

# Что не учтено на уровне замысла

Это не баги — это отсутствующие решения. Они дороже любой карточки выше, потому что определяют, придётся ли переписывать.

### 1. Приложение написано для человека со свободными руками

Водитель пользуется им между рейсами, часто на ходу, одной рукой, на солнце. При этом: ввод суммы заправки — через `prompt()`; удаление — через `confirm()`; ошибочное завершение свайпом — **необратимо**, отмены нет; кнопки-иконки без подписей; крестики модалок маленькие. HUD-режим — единственная уступка этому сценарию, и он самый проработанный экран в приложении. Остальное спроектировано для десктопа — что подтверждается и конфигом Lighthouse с `preset: "desktop"`.

### 2. Два владельца не могут вести общий график

Модель прямо предполагает 2–3 владельцев (`ownersCount`, деление прибыли 50/50 или 33/33/33). Но данные лежат в IndexedDB **одного устройства**. Два человека физически не могут работать с одним расписанием: у каждого свой список поездок, свои конфликты, своя выручка. Приложение считает совместный бизнес, но обслуживает одного пользователя. Это не «добавить синк потом» — это меняет модель данных (кто владелец записи, кто её изменил, как разрешать расхождения). Решение отложено, но не зафиксировано как решение.

### 3. Часовой пояс не существует как понятие

См. P1-01. Даты то UTC, то локальные, в зависимости от места в коде. Для приложения, вся суть которого — «во сколько забрать клиента», время должно быть явным типом с явной зоной, а не строкой `'HH:MM'` рядом со строкой `'YYYY-MM-DD'`.

### 4. Нет версионирования схемы данных

`DB_VERSION = 1`, обработчик `onupgradeneeded` только создаёт стор. Миграций нет. При этом форма записи уже менялась: в демо-данных `FuelStore` есть поле `odo`, а `addFuelLog()` его **не пишет** — то есть в хранилище уже сосуществуют две формы записи, и код, который прочитает `log.odo`, получит `undefined` на всех настоящих данных. Ключ `localStorage` `'taxi_calc_state'` версии не имеет вовсе (у `FuelStore` — имеет, `_v1`). Первая же смена структуры сломает данные тех, кто уже пользуется.

### 5. Обработка ошибок не является слоем

Паттерн по всему коду: `try { ... } catch (e) { console.error(...) }`. На телефоне консоли нет. Любой сбой выглядит как «пусто» или «ничего не произошло». Для offline-first приложения без бэкенда, где данные существуют в одном экземпляре, молчание — самый опасный из возможных ответов. Нужен единый канал: видимая пользователю ошибка + журнал, который можно приложить к экспорту.

### 6. Тесты проверяют, что код работает — не что он не ломается

11 тестов, все зелёные, все по счастливому пути сторов. **Ноль** тестов на: `utils.js` (единственный защитный слой), `flight.service.js` (самая сложная логика), деление на ноль, повреждённый `localStorage`, отказ IndexedDB, часовые пояса, экранирование. `CLAUDE.md` объявляет `npm test` гейтом бизнес-логики — гейт проходит любое из перечисленных выше нарушений.

### 7. Дизайн-система заявлена, но не является ограничением

`CLAUDE.md`: «Все цвета берутся ТОЛЬКО из `tokens.css`, hex в JS запрещён». Фактически — 14 хардкодов в `calculator.view.js` (P3-01) и множество инлайновых `style=` в `trips.view.js`. Правило без проверки — это не правило. ESLint, который мог бы его проверять, установлен и не настроен (P3-02).

# Что сделано хорошо

Чтобы карта была честной, а агенты не «улучшили» то, что улучшать не надо:

- **Разделение Store/View выдержано строго.** Ни один стор не трогает DOM. Это редкость в ванильных проектах и главная причина, почему всё вышеперечисленное чинится точечно, а не переписыванием.
- **Идея `SafeHTML` как типа правильная.** Различать «сырой текст» и «доверенная разметка» на уровне типа, а не соглашения — это грамотное решение. Дефект в P2-01 — в реализации одной ветки, не в замысле.
- **Ставка НДС 13% применена верно.** Это пониженная ставка Греции для пассажирских перевозок, и формула `gross / 1.13` вычленяет налог корректно — частая ошибка «вычесть 13%» здесь не допущена.
- **`generateGCalLink` обрабатывает время правильно**: локальный парсинг → `toISOString()` даёт корректный UTC. Проверено отдельно, ошибки нет.
- **Ленивое получение canvas-контекста** в `renderChart` (`canvas may be in hidden tab at boot`) — автор нашёл и осознанно закрыл реальный баг.
- **Захват `e.currentTarget` до асинхронного колбэка View Transition** в `app.js` с комментарием-объяснением — знание тонкого места платформы.
- **Тесты существуют и зелёные**, скрипт сборки SW существует, LHCI подключён. Каркас качества построен — ему не хватает зубов, а не наличия.
